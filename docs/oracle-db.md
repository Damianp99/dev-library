## Panoramica

Oracle Database è un RDBMS enterprise che offre ACID, SQL e PL/SQL, partizionamento avanzato, RAC (Real Application Clusters) per scalabilità orizzontale e Data Guard per disaster recovery. È tipico in ambienti corporate, applicazioni legacy e contesti con requisiti stringenti di HA, compliance e integrazione con l’ecosistema Oracle.

Per dettagli su licenze e costi vedi [Licensing e costi](#licensing-e-costi); i fatti tecnici qui descritti si riferiscono alla documentazione Oracle (schema, PL/SQL, RAC, Data Guard).

!!! tip "Prova a spiegarlo"
    Spiega a voce: cos'è **RAC** e in che modo **Data Guard** si differenzia dalla replica in lettura. Poi verifica nelle sezioni sotto.

## Schema e namespace

**Definizione**  
In Oracle uno schema è un contenitore di oggetti (tabelle, viste, procedure, sequence) associato a un utente. Il nome completo di un oggetto è `schema.oggetto`; in contesti multi-tenant o per applicazioni diverse si usano spesso schema separati. Lo spazio di nomi include tabelle, viste, synonym (alias per oggetti di altri schema).

**Caso d'uso**  
Separare dati e logica per applicazione o ambiente (es. schema APP_PROD, APP_STAGING); usare synonym per nascondere lo schema reale; gestire permessi a livello di schema (GRANT su oggetti o ruoli).

**Esempio**

```sql
-- Creazione schema (utente)
CREATE USER app_user IDENTIFIED BY password
  DEFAULT TABLESPACE users QUOTA UNLIMITED ON users;

-- Tabella nello schema
CREATE TABLE app_user.ordini (
  id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  cliente_id NUMBER NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Synonym per altro schema
CREATE PUBLIC SYNONYM ordini FOR app_user.ordini;
```

**Impatto su performance e consistenza**  
Schema multipli permettono isolamento logico; troppi schema e synonym possono complicare manutenzione e dipendenze. I tablespace definiscono dove sono allocati i dati (disco) e influenzano backup e performance I/O.

**Errore tipico**  
Hardcodare il nome schema nell’applicazione invece di usare synonym o connection con schema di default; non gestire le quote sui tablespace (rischio di riempimento).

## PL/SQL e stored procedure

**Definizione**  
PL/SQL è il linguaggio procedurale di Oracle: blocchi anonimi, procedure, function, package (raggruppamento di procedure/funzioni e variabili). Esegue logica lato server con accesso diretto ai dati, riducendo round-trip e permettendo vincoli e business rule centralizzati.

**Caso d'uso**  
Logica complessa che coinvolge più tabelle con transazioni e gestione errori; validazioni e trasformazioni da esporre come API; batch e job schedulati (DBMS_SCHEDULER); riduzione carico di rete spostando elaborazione nel DB.

**Esempio**

```sql
-- Procedura con transazione
CREATE OR REPLACE PROCEDURE trasferisci_saldo (
  p_from_id NUMBER, p_to_id NUMBER, p_importo NUMBER
) AS
BEGIN
  UPDATE conti SET saldo = saldo - p_importo WHERE id = p_from_id;
  IF SQL%ROWCOUNT <> 1 THEN
    RAISE_APPLICATION_ERROR(-20001, 'Conto sorgente non trovato o saldo insufficiente');
  END IF;
  UPDATE conti SET saldo = saldo + p_importo WHERE id = p_to_id;
  COMMIT;
EXCEPTION
  WHEN OTHERS THEN
    ROLLBACK;
    RAISE;
END;
```

**Impatto su performance e consistenza**  
Le procedure riducono round-trip e possono ridurre lock se la logica è ben strutturata; logica pesante in PL/SQL può caricare l’istanza e rendere il tuning più difficile. Testabilità e versioning richiedono disciplina (migrazioni, test).

**Errore tipico**  
Mettere troppa logica di business in PL/SQL senza test automatici; non gestire eccezioni (NO_DATA_FOUND, TOO_MANY_ROWS) o fare COMMIT/ROLLBACK incoerenti; ignorare il costo di contest switch tra SQL e PL/SQL per operazioni molto semplici.

## Sequence e identità

**Definizione**  
Una sequence è un oggetto che genera numeri sequenziali (NEXTVAL, CURRVAL); è indipendente dalle tabelle e può essere condivisa. Da Oracle 12c è disponibile anche IDENTITY (GENERATED BY DEFAULT AS IDENTITY) sulla colonna, simile agli auto-increment di altri DB.

**Caso d'uso**  
Chiavi surrogate per tabelle; numerazione ordini o fatture; ID univoci senza dipendere da INSERT multipli nella stessa transazione (sequence garantisce valori distinti anche tra sessioni).

**Esempio**

```sql
-- Sequence classica
CREATE SEQUENCE ordini_seq START WITH 1 INCREMENT BY 1 NOCACHE;

INSERT INTO ordini (id, cliente_id) VALUES (ordini_seq.NEXTVAL, 100);

-- Colonna IDENTITY (12c+)
CREATE TABLE ordini (
  id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  cliente_id NUMBER NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**Impatto su performance e consistenza**  
Sequence con CACHE riducono accessi al data dictionary; NOCACHE è più sicuro in RAC per evitare “buchi” in caso di failover. L’IDENTITY semplifica lo schema ma è legato alla singola colonna/tabella.

**Errore tipico**  
Usare CURRVAL prima di NEXTVAL nella stessa sessione (errore); in RAC, cache troppo grandi possono produrre gap in sequenza in caso di failover; assumere che i valori siano consecutivi senza gap (non garantito con cache).

## Partizionamento

**Definizione**  
Il partizionamento divide una tabella (e i relativi indici) in parti (partition) in base a un criterio: range (es. per data), list (valori discreti), hash (distribuzione uniforme), interval (range con creazione automatica partizioni). Partition pruning permette al motore di accedere solo alle partizioni rilevanti per la query.

**Caso d'uso**  
Tabelle molto grandi (fatti, log): manutenzione (archiviazione, drop di partizioni vecchie), query che filtrano per chiave di partizione (es. data), parallelismo e backup per partizione.

**Esempio**

```sql
-- Partizionamento per range (data)
CREATE TABLE eventi (
  id NUMBER,
  created_at TIMESTAMP,
  payload CLOB
) PARTITION BY RANGE (created_at) (
  PARTITION p_2024_01 VALUES LESS THAN (TO_DATE('2024-02-01','YYYY-MM-DD')),
  PARTITION p_2024_02 VALUES LESS THAN (TO_DATE('2024-03-01','YYYY-MM-DD')),
  PARTITION p_max VALUES LESS THAN (MAXVALUE)
);

-- Query: partition pruning se il filtro usa created_at
SELECT * FROM eventi WHERE created_at >= DATE '2024-02-01' AND created_at < DATE '2024-03-01';
```

**Impatto su performance e consistenza**  
Partition pruning riduce I/O e costo delle query; le operazioni DDL (DROP PARTITION, TRUNCATE PARTITION) sono molto più veloci che su tabella intera. Indici globali vs locali: globali sono più flessibili ma costosi da manutenere su partizioni.

**Errore tipico**  
Partizionare senza che le query filtrino sulla chiave di partizione (nessun pruning); usare partizioni con troppi o troppo pochi dati (sbilanciamento); dimenticare di creare partizioni nuove in schema range (o usare INTERVAL).

## RAC e alta disponibilità

**Definizione**  
Real Application Clusters (RAC) permette a più istanze Oracle di accedere allo stesso database (storage condiviso, tipicamente ASM). In caso di guasto di un’istanza, le altre continuano a servire le richieste; il connection pooling lato client (es. Oracle Connection Manager, UCP) può indirizzare le connessioni e gestire il failover.

**Caso d'uso**  
HA e scalabilità orizzontale per carico di lettura e scrittura; riduzione del single point of failure a livello di istanza; necessità di uptime elevato senza dipendere da un solo server.

**Esempio**

Architettura tipica: due o più nodi RAC, storage condiviso (ASM), client che si connettono a un servizio (service name) con failover configurato (TAF, Fast Application Notification). In caso di crash di un nodo, le sessioni possono essere rilevate dall’altro nodo (con possibili rollback delle transazioni in corso).

**Impatto su performance e consistenza**  
RAC introduce overhead di coordinamento (block transfer tra istanze, global lock); le applicazioni devono essere tolleranti a failover (retry, idempotenza). Il licensing Oracle è per core/processor e in RAC si paga per tutti i core dei nodi attivi.

**Errore tipico**  
Assumere che RAC raddoppi le performance (è soprattutto HA); applicazioni non idempotenti che non gestiscono disconnessioni e retry; sottovalutare costi di licenza e complessità operativa (patch, upgrade).

## Data Guard

**Definizione**  
Data Guard fornisce replica e disaster recovery: un database primary e uno o più standby (fisici o logici). La replica fisica applica i blocchi redo; quella logica applica le modifiche a livello SQL. Standby può essere usato per read-only (Active Data Guard, opzione a pagamento) o solo per failover.

**Caso d'uso**  
DR: sito secondario per failover in caso di disastro; offload di letture su standby (con Active Data Guard); backup e report su standby per non caricare il primary.

**Esempio**

Configurazione tipica: primary che invia redo allo standby; broker (Data Guard broker) per monitoraggio e failover/switchover. Dopo un failover, lo standby diventa primary; il vecchio primary può essere riconfigurato come standby.

**Impatto su performance e consistenza**  
Il primary invia redo in modo asincrono o sincrono (SYNC con zero data loss). Le letture su standby vedono dati con ritardo (lag); in caso di failover si può perdere l’ultimo insieme di transazioni se la replica è asincrona.

**Errore tipico**  
Confondere Data Guard con RAC: RAC è multi-istanza su stesso storage; Data Guard è replica su altro sito. Non testare il failover; non monitorare il lag di replica quando si usano letture sullo standby.

## Licensing e costi

!!! warning "Verifica con il fornitore"
    Licenze, costi e condizioni Oracle vanno confermati con Oracle o con il proprio fornitore. Questa guida non costituisce consulenza legale o commerciale; per inventario, audit e conformità fare riferimento alla documentazione ufficiale Oracle e ai contratti in essere.

**Definizione**  
Oracle Database è a licenza: si paga per processor/core (o per utente nominale, a seconda del prodotto). Opzioni come RAC, Data Guard (Advanced Security, Active Data Guard, RAC), partitioning e altri componenti hanno costi aggiuntivi. L’uso non conforme (es. virtualizzazione senza licensing corretto) espone a audit.

**Caso d'uso**  
Valutare il costo totale (licenza, supporto, HA, tool) prima di standardizzare su Oracle; in contesti cloud considerare Oracle Cloud o licenza bring-your-own-license (BYOL).

**Impatto**  
I costi possono essere molto superiori a RDBMS open source (PostgreSQL, MySQL); in cambio si ha supporto enterprise, tooling e integrazione con stack Oracle (Fusion, E-Business, ecc.).

**Errore tipico**  
Sottovalutare i costi di licenza (soprattutto in RAC e con opzioni); usare funzionalità a pagamento senza licenza; non documentare l’inventario delle istanze e delle opzioni per gli audit.

## Quando usare Oracle

**Definizione**  
Oracle è una scelta tipica in ambienti enterprise dove esistono già competenze, contratti e integrazioni (ERP, applicazioni custom Oracle). È adatto a carichi critici con requisiti di HA (RAC, Data Guard), compliance e supporto formale.

**Caso d'uso**  
Applicazioni legacy Oracle; settori (finance, PA) con standard e audit che privilegiano Oracle; necessità di RAC, Data Guard, partitioning avanzato e supporto 24/7; integrazione con stack Oracle (middleware, app server).

**Impatto**  
Maggiore costo e complessità operativa; in cambio, ecosistema maturo, strumenti e competenze diffuse in grandi organizzazioni.

**Errore tipico**  
Scegliere Oracle “per default” senza valutare requisiti reali e costi; migrare a Oracle solo per status senza bisogno di funzionalità specifiche.

## Errori comuni

- **Gestione connessioni**: non usare connection pooling (Oracle UCP, OCI pool) con molti thread; esaurimento di sessioni e contenzione su risorse condivise.
- **Tuning**: ignorare statistiche (DBMS_STATS), piani di esecuzione (EXPLAIN PLAN, AWR) e indici; query lente senza analisi sistematica.
- **Transazioni e lock**: transazioni lunghe che bloccano righe; mancata gestione di deadlock e ORA-00060; COMMIT/ROLLBACK incoerenti in procedure.
- **Schema e permessi**: grant eccessivi (DBA a app); oggetti in schema sbagliato; synonym non aggiornati dopo migrazioni.
- **Backup e recovery**: non testare il restore; non considerare RPO/RTO e la configurazione Data Guard in base a essi.

- Oracle: RDBMS enterprise, ACID, PL/SQL, partizionamento (range, list, hash), RAC (multi-istanza su storage condiviso), Data Guard (replica e DR).
